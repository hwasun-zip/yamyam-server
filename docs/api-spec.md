# yamyam 제휴사 추천 API 명세 및 운영 매뉴얼

> 상태: 2026.11. 현재 서버(`/api/v1/recommendations`)를 외부 제휴사에 제공한다고 가정하고, 제공에 필요한 인증, 호출 제한, 오류 규격, 운영 절차를 정의한다. API 키 인증, 호출 제한, 오류 규격은 서버에 구현하고 테스트로 검증했다. 각 항목의 구현 여부는 8장에 정리했다.

## 1. 개요

### 왜 제휴사 API인가
yamyam-web v2 이후, 강남구 밖 접속 10회에서 추천 음식으로 **카카오맵, 네이버 지도의 내 주변 검색**이 9회 나왔다. 사용자는 yamyam에서 "무엇을 먹을지"를 정하고, 실제 가게 탐색은 지도 앱에서 했다.

그렇다면 yamyam이 가게 목록까지 직접 갖고 있을 필요 없이, **"오늘 날씨에 무엇을 먹을지"라는 판단만 API로 제공**하면 지도 앱, 배달 앱, 사내 식당 앱 등이 자기 서비스 안에서 바로 쓸 수 있다. 음식점 데이터가 강남구로 한정된 문제도, 음식점 정보를 이미 가진 제휴사와 붙으면 자연스럽게 풀린다.

### 제공 범위
| 제공 | 이유 |
| --- | --- |
| 날씨 기반 음식 추천 (음식 순위 + 점수 + 이유) | yamyam의 핵심 가치. 개인정보가 필요 없다 |
| 강남구 음식점 목록 | 선택 제공. 자체 가게 데이터가 없는 제휴사용 |
| **쿠폰 발급** | **제휴사에 사용자 식별값 전달이 필요한 쿠폰 발급 연동은 제공하지 않는다.** 아래 참고 |

**쿠폰 발급을 제휴사에 열지 않는 이유**: 쿠폰은 본인확인(L2)을 거친 사람 단위로 1매만 발급한다 (`docs/auth-design.md`). 제휴사가 대신 발급하려면 사용자의 본인확인 식별값을 제휴사와 주고받아야 하는데, 이는 개인정보를 제3자와 공유하는 일이라 별도의 동의와 법적 검토가 필요하다. 쿠폰 발급 자체가 제3자 제공인 것은 아니고, 제휴사가 발급 주체가 되면 1인 1매 확인을 위해 식별값이 제휴사로 넘어가는 구조가 된다는 점이 문제다. 그래서 쿠폰은 yamyam 자체 화면에서만 발급하고, 제휴사 API는 **개인정보가 전혀 오가지 않는 추천 기능**으로 범위를 제한한다.

## 2. 제휴사 인증

제휴사 API 호출의 주체는 개인이 아니라 **기관**이다. 그래서 사용자 로그인이 아니라 제휴사별 API 키로 확인한다 (`docs/auth-design.md`의 수준 P).

### API 키
- 모든 요청에 `X-API-Key` 헤더를 넣는다.
- 키는 두 종류를 발급한다.

| 종류 | 접두어 | 용도 | 호출 한도 |
| --- | --- | --- | --- |
| 테스트 키 | `yk_test_` | 개발, 연동 테스트 | 분당 30회 |
| 운영 키 | `yk_live_` | 실제 서비스 | 분당 600회 (계약에 따라 조정) |

- 서버는 키 원문을 저장하지 않고 **해시만 저장**한다. 키 원문은 발급 순간 한 번만 보여준다.
- 키는 브라우저나 앱 코드에 넣지 않고, 반드시 **제휴사 서버에서만** 호출한다. 앱에 넣으면 누구나 꺼내 쓸 수 있다.

### 키 교체와 폐기
| 상황 | 절차 |
| --- | --- |
| 정기 교체 (권장 1년) | 새 키 발급 → 두 키를 7일간 함께 허용 → 기존 키 폐기 |
| 유출 의심 | 즉시 폐기 → 새 키 발급 → 폐기 시점 이후 호출 기록 확인 |
| 계약 종료 | 종료일 0시에 폐기 |

## 3. 엔드포인트

### `GET /api/v1/recommendations`
위치(와 선택적으로 날씨)를 받아 오늘 먹을 음식 순위와 근처 음식점을 돌려준다.

**요청 파라미터**

| 이름 | 필수 | 형식 | 기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `lat` | O | 실수 | | 위도. 33.0 ~ 39.0 (대한민국 범위) |
| `lng` | O | 실수 | | 경도. 124.0 ~ 132.0 |
| `temp` | | 실수 (°C) | | 기온. 넣으면 실시간 날씨 대신 이 값을 쓴다 |
| `precip` | | 실수 (mm) | 0 | 강수량. `temp`가 있을 때만 쓴다 |
| `humidity` | | 실수 (%) | 60 | 습도. 0 ~ 100 |
| `wind` | | 실수 (m/s) | 2 | 풍속 |
| `topFoods` | | 정수 | 3 | 돌려줄 음식 수. 1 ~ 5 |
| `radiusKm` | | 실수 | 3.0 | 음식점 검색 반경. 0.1 ~ 10 |
| `limit` | | 정수 | 10 | 돌려줄 음식점 수. 0 ~ 50. 음식 순위만 필요하면 0 |

**요청 예시**
```http
GET /api/v1/recommendations?lat=37.4979&lng=127.0276&limit=3
X-API-Key: yk_live_xxxxxxxxxxxxxxxx
```

**응답 예시 (200)**
```json
{
  "weather": { "temp": 18.0, "precip": 20.0, "humidity": 90.0, "wind": 3.0, "source": "REALTIME" },
  "topFoods": [
    { "food": "칼국수", "score": 1.6 },
    { "food": "파전",   "score": 1.5 },
    { "food": "국밥",   "score": 0.5 }
  ],
  "restaurants": [
    { "name": "등촌샤브칼국수 강남역점", "category": "칼국수", "distanceKm": 0.15 },
    { "name": "윤대감 빈대떡",          "category": "파전",   "distanceKm": 0.21 }
  ]
}
```

**응답 필드**

| 필드 | 설명 |
| --- | --- |
| `weather` | 추천에 쓴 날씨. 실시간 조회값 또는 요청에 넣은 값 |
| `weather.source` | `REALTIME`(실시간 조회) / `FALLBACK`(날씨 API 장애로 기본값 사용) / `REQUEST`(요청에 넣은 값). `FALLBACK`이면 실제 날씨와 다를 수 있으니 제휴사 화면에서 안내를 권장한다 |
| `topFoods[].score` | 이 날씨에 그 음식이 **평소보다 얼마나 더 검색되는지** (표준점수). 0이 평소, 1.0 이상이면 꽤 많이 찾는 날 |
| `restaurants[].distanceKm` | 요청 위치로부터의 직선거리 (km) |

**제휴사 화면 표시 권장 사항**
- `score`는 숫자 그대로 보여주지 않는다. yamyam-web v1에서 "+0.6이 무슨 의미인지 모르겠다"는 의견이 나왔고, v2에서 "평소보다 0.6↑"처럼 바꾼 뒤 해결됐다. 같은 방식을 권장한다.

## 4. 호출 제한

- 키별로 분당 호출 수를 센다 (2장 표 참고).
- 모든 응답에 남은 횟수를 헤더로 알려준다.

| 헤더 | 의미 |
| --- | --- |
| `X-RateLimit-Limit` | 분당 한도 |
| `X-RateLimit-Remaining` | 이번 1분 동안 남은 횟수 |
| `Retry-After` | 한도 초과 시, 몇 초 뒤 다시 호출할 수 있는지 |

- **같은 위치는 10분간 같은 날씨를 쓴다.** 서버가 좌표를 약 1km 격자로 묶어 날씨를 캐싱하기 때문이다. 제휴사도 같은 위치의 결과를 몇 분간 저장해 두고 쓰면 호출 수를 크게 줄일 수 있다. (서버 실측: 캐시 적중 시 응답 9.6ms, 미적중 1,125ms)

## 5. 오류 규격

모든 오류는 같은 형식으로 돌려준다.
```json
{ "code": "INVALID_PARAMETER", "message": "lat는 33.0 ~ 39.0 범위여야 합니다", "field": "lat" }
```

| HTTP | code | 의미 | 제휴사 대응 |
| --- | --- | --- | --- |
| 400 | `INVALID_PARAMETER` | 파라미터 누락, 형식 오류, 범위 밖 | `field`를 보고 요청 수정. 재시도하지 않는다 |
| 401 | `API_KEY_MISSING` | `X-API-Key` 헤더 없음 | 헤더 추가 |
| 401 | `API_KEY_INVALID` | 없는 키, 폐기된 키 | 포털에서 키 상태 확인 |
| 403 | `KEY_SCOPE_DENIED` | 테스트 키로 운영 서버 호출 등 | 맞는 키 사용 |
| 429 | `RATE_LIMITED` | 분당 한도 초과 | `Retry-After`초 뒤 재시도 |
| 500 | `INTERNAL_ERROR` | 서버 내부 오류 | 잠시 뒤 1회 재시도, 반복되면 문의 |

**재시도 원칙**: 400, 401, 403은 다시 보내도 결과가 같으므로 재시도하지 않는다. 429와 500만 재시도하며, 500은 1초, 2초, 4초 간격으로 최대 3회까지 한다.

## 6. 운영 매뉴얼

### 6.1 제휴 신청부터 운영까지

| 단계 | 제휴사가 하는 일 | yamyam이 하는 일 | 기간 |
| --- | --- | --- | --- |
| 1. 신청 | 포털에서 회사 정보, 사용 목적, 예상 호출량 제출 | 사용 목적 검토 | 1~3일 |
| 2. 테스트 | 테스트 키로 연동 개발 | 연동 문의 대응 | 제휴사 일정 |
| 3. 연동 점검 | 점검 항목(6.2) 확인 결과 제출 | 호출 기록으로 점검 결과 확인 | 1일 |
| 4. 운영 키 발급 | 운영 키 수령, 서버에 안전하게 보관 | 키 발급, 한도 설정 | 당일 |
| 5. 운영 | 서비스 출시 | 모니터링(6.3) | 계속 |

### 6.2 운영 키 발급 전 연동 점검 항목
- [ ] API 키를 제휴사 서버에서만 호출한다 (앱, 웹 화면 코드에 키가 없다)
- [ ] 400, 401, 403 오류에 재시도하지 않는다
- [ ] 429 응답 시 `Retry-After`를 지킨다
- [ ] 같은 위치의 결과를 일정 시간 저장해 재사용한다
- [ ] `score`를 사용자에게 숫자 그대로 보여주지 않는다 (권장)

### 6.3 모니터링 지표 (초기 설계값)

> 아래 기준은 부하 테스트 실측값(p95 177ms, 동시 50명)을 바탕으로 정한 초기 설계값이다. 실제 운영 데이터가 쌓이면 다시 조정한다.

| 지표 | 정상 | 대응 기준 |
| --- | --- | --- |
| 오류율 (5xx 비율) | 0.1% 미만 | 5분간 1% 이상이면 장애로 판단 |
| 응답 시간 p95 | 200ms 미만 (실측 177ms, 동시 50) | 5분간 1초 이상이면 날씨 API 상태 확인 |
| 날씨 기본값 사용 비율 | 0% | 1% 이상이면 날씨 API 장애 의심 |
| 키별 429 비율 | 1% 미만 | 지속되면 제휴사에 한도 상향 또는 캐싱 안내 |

### 6.4 장애 대응

| 상황 | 서버 동작 | 운영자 조치 | 제휴사 안내 |
| --- | --- | --- | --- |
| 외부 날씨 API 장애 | 기본 날씨(20°C, 비 없음)로 추천을 계속 제공하고 `weather.source`를 `FALLBACK`으로 표시. 기본값은 캐시하지 않아, 날씨 API가 복구되면 다음 요청부터 바로 실시간 날씨로 돌아간다 | 날씨 API 상태 확인, 복구 시각 기록 | 장애가 30분 이상이면 공지. 이 동안의 추천은 실제 날씨와 다를 수 있음 |
| 서버 장애 | 500 응답 | 복구 후 원인과 재발 방지책 정리 | 장애 시작, 복구 시각, 원인을 공지 |
| 키 유출 신고 | | 즉시 폐기, 새 키 발급 (2장) | 해당 제휴사에만 개별 안내 |

### 6.5 버전 정책
- 주소에 버전을 둔다 (`/api/v1/`).
- **필드 추가는 같은 버전에서 한다.** 제휴사는 모르는 필드를 무시하도록 구현한다.
- **필드 삭제, 이름 변경, 의미 변경은 새 버전(`/v2/`)으로 한다.** 기존 버전은 새 버전 공지 후 최소 6개월 유지한다.
- 변경 사항은 포털 공지와 등록된 담당자 이메일로 30일 전에 알린다.

## 7. 제휴사 포털에 필요한 화면 (기획안, 미구현)

| 화면 | 기능 |
| --- | --- |
| 제휴 신청 | 회사 정보, 사용 목적, 예상 호출량 입력 |
| 키 관리 | 테스트 키, 운영 키 발급과 폐기. 키 원문은 발급 시 한 번만 표시 |
| 사용량 | 일별, 분별 호출 수와 오류 코드별 비율 |
| 문서 | 이 명세, 변경 이력, 장애 공지 |
| 담당자 | 연락처 관리 (장애, 변경 공지 수신) |
