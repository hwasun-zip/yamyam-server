# yamyam 인증 설계안

> 상태: 설계안 (2026.11). 이 중 "1인 1매 쿠폰 발급"은 서버에 구현하고, 본인확인 연동은 실제 본인확인기관 계약이 필요해 모의(mock) 방식으로 검증한다.

## 1. 왜 인증이 필요해졌나

yamyam은 지금까지 로그인 없이 동작했다. 날씨로 음식을 추천하고 가까운 맛집을 보여주는 데는 "누구인지"가 필요 없었기 때문이다. 그런데 서비스를 운영하면서 두 군데에서 사용자 식별이 필요해졌다.

**① 사용자 의견 (yamyam-web 설문)**
- 취향 반영 요청 4건: "매운맛 같은 취향을 고려했으면"
- 리뷰 기능 요청 2건: "이용한 사람들이 남길 수 있는 리뷰창"
- 취향은 "다음에 와도 같은 사람"임을 알아야 저장할 수 있고, 리뷰는 작성자를 알아야 도배와 허위 리뷰를 막을 수 있다.

**② 선착순 쿠폰의 구멍 (yamyam-server)**
- 원자적 UPDATE로 "총 100장 초과 발급"은 막았다.
- 하지만 발급 API(`POST /coupons/{id}/issue`)는 누가 요청했는지 받지 않는다. **한 사람이 100번 요청하면 100장을 모두 가져갈 수 있다.**
- 수량의 정합성은 지켰지만, 공정성(1인 1매)은 지키지 못한 상태다.

## 2. 설계 원칙

1. **필요한 만큼만 확인한다.** 모든 기능에 로그인을 요구하면 지금의 핵심 경험(접속하자마자 추천)이 깨진다. 기능의 위험도에 맞춰 확인 수준을 다르게 둔다.
2. **필요할 때 한 단계 올린다 (단계별 인증).** 처음부터 본인확인을 요구하지 않고, 쿠폰처럼 위험이 큰 기능을 쓰는 순간에만 추가 확인을 요청한다.
3. **최소한으로 수집한다.** 이름, 생년월일, 휴대폰 번호를 서비스가 직접 보관하지 않는다. 중복 확인에 필요한 값만, 원문이 아닌 형태로 보관한다.

## 3. 기능별 인증 수준

> L0~L3는 이 프로젝트에서 기능의 위험도에 따라 직접 정의한 수준이며, 업계 공식 등급이 아니다. 사용자 인증(L0~L3)과 제휴기관 호출자 인증(P)은 확인 대상이 달라 따로 구분한다.

| 수준 | 의미 | 확인 방법 |
| --- | --- | --- |
| L0 | 누구인지 모름 | 없음 |
| L1 | 같은 계정인지 앎 | 소셜 로그인 (카카오 등) |
| L2 | 같은 사람인지 앎 | 휴대폰 본인확인 (본인확인기관 연동) |
| L3 | 그 사람이 그 내용에 동의했다는 증적을 남김 | 인증서 기반 전자서명 (확장 설계) |
| P (제휴기관 호출자 인증) | 어느 제휴사인지 앎 | API 키 (사람이 아닌 기관 단위) |

| 기능 | 수준 | 이유 |
| --- | --- | --- |
| 날씨 기반 추천 보기 | L0 | 누가 써도 피해가 없다. 첫 경험을 막지 않는 게 더 중요하다 |
| 지도 앱 연결, 음식 직접 고르기 | L0 | 위와 같음 |
| 취향 저장 | L1 | 다음 방문에도 같은 계정이면 충분하다 |
| 리뷰 작성 | L1 | 작성자에게 책임을 묻고, 같은 계정의 반복 작성을 제한할 수 있으면 된다 |
| 선착순 쿠폰 발급 | **L2** | 아래 4장 참고 |
| 제휴사 추천 API 호출 | P | 호출 주체가 개인이 아니라 기관이다 (`docs/api-spec.md`) |
| 제휴 계약 체결 (제휴사 포털) | L3 | 계약 의사를 확인하고, 서명 뒤 내용이 바뀌지 않았음을 검증할 수 있는 증적을 남겨야 한다. 확장 설계 |

### 실제 인증 제도와의 대응

| 수준 | 실제 제도 | 이 설계에서 쓰는 것 |
| --- | --- | --- |
| L2 본인확인 | 정보통신망법에 따라 방송미디어통신위원회가 지정한 **본인확인기관**이 주민등록번호 대신 본인확인 결과와 연계정보(CI)를 제공 | CI를 "같은 사람" 판별 기준으로 사용 |
| L3 전자서명 | 전자서명법 제8조에 따라 평가기관의 평가를 거쳐 운영기준 준수사실의 인정을 받은 **전자서명인증사업자**의 인증서로 서명 | 서명 결과(누가, 언제, 무엇에)를 계약 기록과 함께 보관 |

- 본인확인기관 지정은 2025년 10월 방송통신위원회가 방송미디어통신위원회로 개편되면서 방송미디어통신위원회가 맡고 있다.
- 2020년 전자서명법 개정으로 공인인증서의 독점적 지위가 없어지고, 여러 사업자의 인증서를 쓸 수 있게 됐다. 서비스는 특정 인증서 하나에 묶이지 않도록, L3 단계를 인증 수단과 분리된 인터페이스로 설계한다.
- 제휴 계약 체결은 지금 yamyam에 없는 기능이다. 제휴사 API(`docs/api-spec.md`)를 실제로 운영한다면 포털에서 계약을 맺게 되므로, 그때 필요한 인증 수준을 미리 정의해 둔다.

## 4. 왜 쿠폰은 소셜 로그인(L1)으로 부족한가

L1로 "계정당 1매"를 걸면, 한 사람이 카카오 계정을 여러 개 만들어 여러 장을 받을 수 있다. 쿠폰은 돈과 같은 가치가 있으므로, 막아야 하는 건 "같은 계정"이 아니라 "같은 사람"의 중복이다.

이를 위해 본인확인 단계(L2)를 둔다. 본인확인기관을 통한 휴대폰 본인확인을 거치면, 서비스는 이름이나 전화번호 대신 **같은 사람이면 항상 같은 값으로 오는 식별값(연계정보, CI)**을 받는다. 계정이 여러 개여도 같은 사람이면 이 값이 같으므로 중복 발급을 막을 수 있다.

### CI도 원문으로 저장하지 않는 이유
CI는 주민등록번호로 만든 일방향 암호화 값이라 주민등록번호로 되돌릴 수는 없다. 하지만 **어느 서비스에서 받아도 같은 값**이다. 그래서 여러 서비스가 CI 원문을 보관하면, 한 곳에서 유출된 CI로 다른 서비스의 이용 이력까지 같은 사람으로 연결할 수 있다. CI를 개인정보로 봐야 한다는 논쟁이 이어지는 이유도 여기에 있다.

yamyam은 "같은 사람인가"만 알면 되므로, CI를 yamyam만 아는 비밀키로 **HMAC-SHA256** 처리한 값만 저장한다 (`UserKeyHasher`, 구현). yamyam 안에서는 같은 사람이 같은 값으로 묶이지만, 저장된 값을 다른 서비스의 CI와 대조할 수 없고, 비밀키 없이는 같은 값을 다시 만들 수도 없다.

다만 HMAC 처리한 값도 yamyam 안에서 특정인을 계속 알아볼 수 있으므로 여전히 개인정보로 다룬다. 원문을 숨긴다고 개인정보 보호 의무가 사라지는 것은 아니다. 그래서 아래를 함께 정한다 (설계).

| 항목 | 기준 |
| --- | --- |
| 처리 목적 | 쿠폰 1인 1매 확인에만 사용. 다른 목적으로 쓰지 않는다 |
| 수집 필요성 | 계정이 여러 개인 같은 사람을 구분하려면 사람 단위 식별값이 필요 |
| 제3자 제공 | 하지 않는다. 제휴사 API에서도 제공하지 않는다 (`docs/api-spec.md` 1장) |
| 보유 기간 | 쿠폰 행사 종료 후 정해진 기간이 지나면 발급 이력의 식별값 파기 |
| 접근 통제 | 비밀키는 환경변수로만 주입하고 코드와 저장소에 두지 않는다. 운영 DB 조회 권한을 최소화한다 |

더 나은 대안도 있다. yamyam의 중복 확인은 서비스 안의 문제이므로, 서비스마다 다른 값으로 발급되는 중복가입확인정보(DI)로도 충분할 수 있다. 다른 서비스와 같은 사람을 연결할 필요가 없다면 DI가 최소 수집 원칙에 더 맞다. 실제 연동 단계에서는 DI를 먼저 검토한다.

### 쿠폰 발급 흐름

```
1. 사용자: 쿠폰 받기 클릭
2. 로그인 안 됨 → 소셜 로그인 (L1)
3. 본인확인 이력 없음 → 휴대폰 본인확인 (L2), 최초 1회
4. 서버: 식별값을 HMAC 처리해서 저장, 원문은 버림
5. 서버: 발급 시도
   - 이 사람(식별값 HMAC)이 이 쿠폰을 이미 받았나? → 받았으면 거절
   - 남은 수량이 있나? → 원자적 UPDATE로 차감
6. 결과 응답: 발급 성공 / 이미 받음 / 품절
```

5번의 두 검사는 동시에 요청이 몰려도 정확해야 한다. "이미 받았나"는 DB의 유일 제약조건(쿠폰 ID + 사용자 식별값)으로, "남은 수량"은 기존의 조건부 원자적 UPDATE로 보장하고, 둘을 하나의 트랜잭션으로 묶는다. 같은 사람이 두 번 동시에 눌러도 한 장만 발급된다.

## 5. 데이터 설계

```
users
  id              PK
  provider        소셜 로그인 제공자 (예: kakao)
  provider_uid    제공자의 사용자 ID
  verified_key    본인확인 식별값의 해시 (본인확인 전에는 NULL)
  UNIQUE (provider, provider_uid)

coupon_issues
  id              PK
  coupon_id       FK
  user_key        발급 기준 식별값 (= users.verified_key)
  issued_at
  UNIQUE (coupon_id, user_key)     ← 1인 1매를 DB가 보장
```

- 서비스가 보관하지 않는 것: 이름, 생년월일, 휴대폰 번호, 식별값 원문
- 식별값은 서비스 비밀키 기반 HMAC-SHA256으로 변환해 저장해, DB가 유출되어도 다른 서비스의 값과 대조할 수 없게 한다.

| `coupon_issues` 테이블과 (쿠폰, 사용자) 유일 제약 | 구현 |

| 보유 기간 경과 후 파기 | 설계만 |
| 소셜 로그인 | 설계만 (요청 헤더의 사용자 식별값으로 대체) |
| 휴대폰 본인확인 연동 | 설계만. 실제 연동은 본인확인기관과의 계약 범위라, 테스트 식별값으로 중복 방지와 동시성만 검증 |

## 7. 한계와 다음 단계

- 실제 본인확인은 본인확인기관과의 계약, 그리고 개인정보 처리에 관한 법적 검토가 필요하다. 이 설계는 흐름과 데이터 구조까지만 다룬다.
- 본인확인 단계가 추가되면 쿠폰을 받기까지 단계가 늘어난다. 이 이탈률은 기존 GoatCounter 클릭 집계로 단계별로 측정해 확인한다.
- 취향 저장과 리뷰(L1)는 소셜 로그인 연동 후 다음 단계에서 구현한다.
