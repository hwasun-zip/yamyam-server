# yamyam-server

날씨 기반 강남구 맛집 추천 **API 서버**.
데이터 분석에서 검증한 "날씨로 음식 수요 예측(Hit@1 58.8%)" 로직을,
실시간 외부 날씨 연동·캐싱·동시성 제어를 갖춘 REST API로 구현했다.
(분석 원본: https://github.com/hwasun-zip/yamyam)

## 기술 스택
Java 25 · Spring Boot 4 · Spring MVC · JPA/Hibernate · H2 · Caffeine Cache · Open-Meteo API · k6

## 실행
```bash
gradle bootRun     # 서버 실행
gradle test        # 동시성 테스트 실행
```

## 주요 API
- `GET /api/v1/recommendations?lat=37.4979&lng=127.0276` — 실시간 날씨 기반 맛집 추천
  - 위치만 주면 실제 날씨 조회 (더운 날 → 냉면·팥빙수 / 비 → 파전), `&temp=32&precip=20`로 수동 테스트 가능
  - 제휴사 공개 API: 헤더 `X-API-Key` 필수. 로컬 시연용 키는 `yk_test_local_demo` (분당 30회)
  - 명세와 운영 매뉴얼: [`docs/api-spec.md`](docs/api-spec.md)
- `GET /api/v1/coupons/{id}` — 맛집 선착순 할인 쿠폰 조회
- `POST /api/v1/coupons/{id}/issue` — 쿠폰 발급 (동시성 안전, 1인 1매)
  - 헤더 `X-User-Identity` 필수 (본인확인 식별값을 대신함). 없으면 401, 이미 받았거나 품절이면 409

## 동작 원리
1. 위치로 실시간 날씨 조회 (Open-Meteo, 좌표를 1km 격자로 캐싱)
2. 날씨값으로 음식별 예측 검색량 계산 후 z-점수 순위화 (학습은 오프라인, 서버는 예측만)
3. 상위 음식 카테고리 음식점을 haversine 거리순으로 반환

## 성능 최적화 (실측)
매 요청의 외부 날씨 API 호출이 병목이었다. 좌표를 약 1km 격자로 양자화한 캐싱(Caffeine, TTL 10분)으로 해결했다.

## 동시성 제어
맛집 선착순 할인 쿠폰(한도 100장) 발급에서 정합성을 보장했다.

- **문제 재현**: 락 없이 구현 시 300개 동시 요청이 한도를 초과 발급하고, 갱신 손실로 카운터가 붕괴(예: 6)
- **해결**: 조건 포함 원자적 UPDATE(`... WHERE issued_count < total`)로 DB 행 단위 직렬화에 위임 → 정확히 100장만 발급
- **검증**: 단위 테스트(CountDownLatch 300스레드) + 실제 API 동시 요청, 두 방식으로 확인
- 계좌 잔액 차감·이체와 동형의 정합성 문제

## 1인 1매 (인증 연계)
수량 정합성은 지켰지만, 발급 API가 요청자를 받지 않아 **한 사람이 100장을 모두 가져갈 수 있는** 구멍이 남아 있었다.
인증 설계(`docs/auth-design.md`)에 따라 쿠폰은 "같은 계정"이 아니라 "같은 사람" 기준으로 1매만 발급한다.

- 요청자 식별값(설계상 본인확인 CI)은 서비스 비밀키 기반 **HMAC-SHA256**으로 변환해서만 저장한다. 원문은 저장하지 않고, 저장된 값은 다른 서비스의 CI와 대조할 수 없다 (`UserKeyHasher`, 표준 검증값 테스트 포함 `UserKeyHasherTest` 3건).
- HMAC 값도 서비스 안에서는 같은 사람을 알아볼 수 있으므로 개인정보로 다룬다. 처리 목적, 보유 기간, 접근 통제 기준은 `docs/auth-design.md` 4장에 정리했다.
- 수량 차감(조건부 원자적 UPDATE)과 발급 이력 저장((쿠폰, 사용자) 유일 제약)을 한 트랜잭션으로 묶었다. 중복이면 이력 저장에서 실패하고, 차감한 수량까지 함께 롤백된다.
- 검증 (`CouponOnePerPersonTest`): 같은 사람 동시 50회 → 1장 / 서로 다른 300명 → 정확히 100장 / 150명이 2번씩 동시 요청 → 100장, 이력도 서로 다른 100명

## 제휴사 API (인증 · 호출 제한 · 오류 규격)
추천 API를 외부 제휴사(지도 앱, 배달 앱 등)에 제공한다고 가정하고, 명세(`docs/api-spec.md`)를 먼저 쓴 뒤 그대로 구현했다.

- **API 키 인증**: 키 원문은 저장하지 않고 SHA-256 해시로만 비교한다. 테스트 키로 운영 서버를 부르면 거절한다 (`KEY_SCOPE_DENIED`).
- **키별 분당 호출 제한**: 응답마다 `X-RateLimit-Limit`, `X-RateLimit-Remaining`을, 초과 시 429와 `Retry-After`를 돌려준다.
- **공통 오류 형식** `{code, message, field}`: 제휴사가 `code`만 보고 재시도 여부를 판단할 수 있다. 범위 검증을 추가해, 이전에 500으로 떨어지던 잘못된 입력(예: 음수 `limit`)을 400으로 바로잡았다.
- **날씨 출처 표시** `weather.source`: 날씨 API 장애로 기본값을 쓴 추천인지 제휴사가 구분할 수 있다. 기본값은 캐시하지 않아 장애가 풀리면 바로 복구된다.
- **쿠폰 API는 제휴사에 열지 않는다**: 쿠폰은 본인확인 식별값이 필요한데, 이를 제휴사와 주고받는 것은 개인정보 제3자 제공이 되기 때문이다.
- 검증: `PartnerApiTest`(인증, 오류 규격, 쿠폰 분리 9건), `PartnerRateLimitTest`(고정 시계로 한도, 429, 다음 분 복구 3건)
